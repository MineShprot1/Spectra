# Spectra Network Dev — сервер доступа к тестовой версии

Это отдельный Cloudflare Worker с базой D1. Он не заменяет рабочий сервер друзей Spectra Network. Репозиторий тестовой версии всегда фиксирован: `MineShprot1/Spectra-Testing`. Адрес публичного репозитория здесь не используется.

## Первое развёртывание через Cloudflare Dashboard

1. Создай Worker **spectra-network-dev**. Открой редактор кода, вставь содержимое `worker.mjs`, опубликуй. В архиве обычные исходники; ZIP не является автоматическим установщиком Cloudflare.
2. Создай базу **D1** с именем **spectra-network-dev**. В SQL Console выполни содержимое `schema.sql`.
3. В настройках Worker добавь D1 binding с именем **DB**, выбрав созданную базу.
4. Создай в GitHub fine-grained token только для **Spectra-Testing**, разрешение **Contents: Read-only**. Добавь его как Secret Worker с именем **GITHUB_TOKEN**. В лаунчер и в выдаваемые ключи он не передаётся.
5. Запусти **Настроить генератор.cmd** в этой папке. Укажи HTTPS-адрес опубликованного Worker. При запросе ADMIN_KEY оставь поле пустым: программа создаст случайный секрет и скопирует его в буфер. Не закрывая программу, сохрани этот секрет в Cloudflare как **ADMIN_KEY**, затем нажми Enter в окне программы.
6. Открой `https://АДРЕС-WORKER/health`. Ответ должен содержать `"ready":true`.

Вместо Dashboard можно использовать Wrangler: `npx wrangler login`, `npx wrangler d1 create spectra-network-dev`, вписать полученный ID в `wrangler.jsonc`, выполнить `npx wrangler d1 execute spectra-network-dev --remote --file=schema.sql`, добавить секреты через `npx wrangler secret put GITHUB_TOKEN` и `npx wrangler secret put ADMIN_KEY`, затем `npx wrangler deploy`.

## Создать одноразовый ключ

После первой настройки запускай **Создать ключ.cmd**. Каждый запуск:

1. Создаёт новый случайный ключ, действительный для ввода в течение 10 минут.
2. Подписывает его локальным ключом разработчика.
3. Регистрирует хеш в серверной базе D1.
4. Копирует ключ в буфер обмена. Вставь его в плашку **Режим тестирования** в настройках обычной версии лаунчера.

При первом успешном вводе запись D1 атомарно закрепляется за установкой. На другом ПК тот же ключ больше не принимается. Доступ установки хранится отдельно, защищённо через Windows DPAPI: при перезапуске и при повторном переходе в тестовую версию новый ключ не требуется. Если ответ сети потерялся, повтор того же запроса с сохранённым секретом исходного ПК восстанавливает активацию; другой ПК этот секрет не получает.

В тестовой версии нет формы ввода ключа. При запуске проверяется сохранённый доступ; при недоступном сервере есть повторная проверка и возврат на обычную версию. Кнопка **Вернуться к обычной версии** запускает её установку. Возврат сохраняет регистрацию ПК, чтобы снова перейти в тестовую без нового ключа.

Личный ключ подписи уже находится на этом ПК в `%LOCALAPPDATA%\SpectraDeveloper\testing-signing-key.pem`. **Он не входит в архив сервера.** Сохрани его резервную копию у себя; не перегенерируй при выпуске очередного ключа. Конфигурация генератора с ADMIN_KEY хранится отдельно в `%LOCALAPPDATA%\SpectraDeveloper\testing-service.dat`, зашифрованная Windows DPAPI. На другом компьютере нужны собственная настройка и восстановленная личная пара подписи.

Если запускать непосредственно Python-файл, команда `py testing_keys.py` делает то же самое. Зависимость — `cryptography`; CMD-файлы устанавливают её в отдельное локальное окружение. Пример изменения времени ввода: `py testing_keys.py issue --minutes 30 --label Developer`. Ключи старого формата `SPTEST1` не являются одноразовыми и в исправленной системе не используются.

## Обновлять сервер с этого ПК

Папку можно оставить на рабочем столе. Для первой авторизации Wrangler используй `npx wrangler login`. В `wrangler.jsonc` впиши ID своей D1. После изменения `worker.mjs` запускай **Обновить сервер.cmd**. Он обновляет только Worker; базу и секреты не удаляет. Повторное выполнение `schema.sql` безопасно: таблицы создаются только при отсутствии.

Обновления самого лаунчера публикуются отдельно: обычные — в `Spectra`, тестовые — в `Spectra-Testing`. Для тестового выпуска увеличивается номер в `testing-build.json` и версия в `launcher-channel.json`. Смешение каналов блокируется по явному манифесту; служебный коммит без изменения версии не вызывает уведомления об обновлении.

## Проверки и отзыв доступа

- `GET /health` — готовность без секретов.
- `POST /admin/keys` — зарегистрировать хеш ключа, только с ADMIN_KEY.
- `POST /admin/revoke` с JSON `{"installationId":"32 шестнадцатеричных символа"}` и заголовком `Authorization: Bearer ADMIN_KEY` — отозвать доступ установки.
- `POST /v1/testing/redeem` — однократное погашение; 409 означает использованный или истёкший ключ.
- `GET /v1/testing/session` — проверка сохранённого доступа.

Сервер хранит хеши ключей и секретов, а не их исходный текст. Запросы к GitHub идут только к фиксированному приватному репозиторию, только для чтения разрешённых маршрутов. Секрет GITHUB_TOKEN остаётся в окружении Cloudflare.

Документация Cloudflare: [D1 prepared statements](https://developers.cloudflare.com/d1/worker-api/prepared-statements/), [Worker Secrets](https://developers.cloudflare.com/workers/configuration/secrets/).
