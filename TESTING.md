# Тестовый канал Spectra

Обычный канал: `MineShprot1/Spectra`, ветка `main`. Тестовый канал: приватный `MineShprot1/Spectra-Testing`, ветка `main`. Выбор канала хранится локально; обычные пользователи остаются на стабильном канале.

## Выпустить ключ доступа

Установить зависимость генератора один раз:

```powershell
py -m pip install cryptography
```

Личная подписывающая пара уже создана на этом ПК. Приватный ключ находится в `%LOCALAPPDATA%\SpectraDeveloper\testing-signing-key.pem`, вне обоих репозиториев. Сохраните его резервную копию у себя. В приложение встроен только `src/Spectra/TestingPublicKey.pem`.

Создать в GitHub **fine-grained personal access token**: выбрать только репозиторий **Spectra-Testing**, дать **Repository permissions → Contents: Read-only**. Не использовать обычный токен с доступом ко всем репозиториям. Его владелец может читать тестовые исходники; этот вариант доступа выбран для данного канала.

Создать отдельный ключ на 90 дней, введя GitHub-токен в скрытом приглашении терминала:

```powershell
py tools/testing_keys.py issue --label "Developer" --days 90 --prompt-token --output "$env:LOCALAPPDATA\SpectraDeveloper\developer.testing-key.txt"
```

Файл назначения должен быть новым: генератор не перезаписывает ранее выданный ключ. Для другого тестировщика укажите другое имя файла и метку. Для автоматизации вместо `--prompt-token` используется переменная окружения `SPECTRA_TESTING_GITHUB_TOKEN`; она не нужна обычным пользователям лаунчера.

Для новой независимой установки системы подписания команда `py tools/testing_keys.py init` создаёт пару только при отсутствии обоих файлов. **Не перегенерировать пару при выпуске очередного ключа доступа**: опубликованные сборки доверяют исходному публичному ключу.

## Войти и выйти

Настройки → **Windows и фоновая работа** → **Войти в режим тестирования**. Вставить полный ключ `SPTEST1.…`. Лаунчер проверяет подпись, назначение и срок действия, затем проверяет чтение приватного репозитория. Только после успеха доступ сохраняется через Windows DPAPI для текущего пользователя.

После входа внизу появляется предложение установить тестовую версию. При следующем запуске обновление выбранного канала устанавливается автоматически по обычным правилам лаунчера. Неверный ключ и недоступный приватный репозиторий не переключают канал.

**Выйти из режима тестирования** удаляет сохранённый доступ и проверяет стабильный канал. Установка предложенного стабильного обновления возвращает сам исполняемый файл; до установки уже запущенная тестовая сборка остаётся тестовой и помечается соответствующим значком. По истечении ключа выбирается стабильный канал. Удаление fine-grained токена в GitHub прекращает доступ к приватным обновлениям для всех ключей, содержащих этот токен.

GitHub-токен находится внутри подписанного ключа доступа; сам формат ключа не шифрует его при передаче. Передавать ключ только конкретному тестировщику. После ввода он хранится зашифрованно и не возвращается в состояние интерфейса. Приватный **ключ подписи** никогда не входит ни в ключи доступа, ни в лаунчер.

## Разрабатывать и собирать

- Обычная папка: `Spectra`. Стабильная версия этого обновления — **0.28.0**.
- Тестовая папка: `Spectra-Testing`. Независимая нумерация начинается с **0.1.0-test.1**.
- Перед выпуском следующей тестовой версии увеличить `number` в `testing-build.json`. Версии станут `0.1.0-test.2`, `0.1.0-test.3` и так далее.
- `pwsh -File Build-Testing.ps1` собирает тестовую версию в `dist/Spectra-Testing`. Можно передать `-Number 2` для разовой локальной сборки; для обновлений из GitHub номер должен быть сохранён в JSON.
- В приватной папке `Directory.Build.props` выбирает тестовый канал и номер по умолчанию. В публичной папке этого файла нет.
- Изменения в публичную папку переносить отдельно. Генератор подписей, приватные GitHub-токены и выданные ключи доступа туда не копировать. Публичный ключ проверки должен совпадать в обоих репозиториях.

Клиент приватного канала обращается только к фиксированному API-адресу `api.github.com/repos/MineShprot1/Spectra-Testing`. Заголовок авторизации задаётся отдельно для каждого запроса и не добавляется в общий HTTP-клиент. Исходники загружаются через Git Blob API с проверкой размеров и Git SHA-1, затем собираются локально существующим механизмом обновления: как и прежде, для него требуется .NET SDK 8 x64. Кэш исходников разделён по каналам.

Документация: [GitHub fine-grained tokens и чтение blob](https://docs.github.com/en/rest/git/blobs#get-a-blob), [ECDSA в Python](https://cryptography.io/en/stable/hazmat/primitives/asymmetric/ec/).
