# Два независимых канала Spectra

Обычная версия **0.28.1**: публичный `MineShprot1/Spectra`. Тестовая **0.1.0-test.2**: приватный `MineShprot1/Spectra-Testing`. Это отдельные репозитории и отдельные каталоги исходников. В публичном проекте нет тестового счётчика и тестового сборочного скрипта.

Обновляющий клиент читает `launcher-channel.json` только из выбранного источника. Для обычных пользователей выбирается исключительно stable. Тестовый канал выбирается только после успешной одноразовой активации через Spectra Network Dev. Подменённый канал или версия другого формата не устанавливаются; название коммита не определяет версию обновления.

## Один раз развернуть сервер

Готовая папка сервера находится на рабочем столе. Полная инструкция: [dev-server/README.md](dev-server/README.md). Нужно создать Worker и D1, добавить серверные секреты ADMIN_KEY и GITHUB_TOKEN, затем настроить локальный генератор по фактическому HTTPS-адресу Worker. GitHub-токен остаётся в Cloudflare; клиент его не получает.

## Выдавать ключи

После настройки запускать **Создать ключ.cmd** из папки сервера либо `py tools/testing_keys.py` в обычной папке. Новый случайный одноразовый ключ регистрируется в D1 и копируется в буфер обмена. По умолчанию его можно ввести в течение 10 минут; это срок первого ввода, а не срок сохранённого доступа.

Секрет подписи остаётся в `%LOCALAPPDATA%\SpectraDeveloper\testing-signing-key.pem`. Зашифрованная настройка генератора — `testing-service.dat` рядом с ним. Эти файлы не входят в репозитории и архив сервера. Публичная пара проверки уже встроена в оба лаунчера.

Старые ключи SPTEST1 больше не используются: они были многократными и не имели серверного погашения. Новая регистрация выполняется один раз, затем сохраняется на ПК; повторные запуски не требуют ввода.

## Пользоваться

1. В обычной версии открыть **Настройки**. Сверху находится плашка **Режим тестирования**.
2. Вставить ключ. Сервер погасит его, а лаунчер сохранит отдельный секрет установки и сразу установит тестовую версию.
3. Тестовая версия автоматически проверит сохранённую регистрацию. В ней нет формы ввода ключа разработчика.
4. Чтобы выйти, нажать **Вернуться к обычной версии**. Лаунчер сразу установит стабильную сборку. Сама регистрация ПК сохраняется: для повторного перехода достаточно кнопки **Перейти в тестовую версию**, без нового ключа.

При неудачной загрузке регистрация не теряется. При потере ответа активации исходный ПК может повторить запрос со своим сохранённым секретом; другой ПК не может повторно использовать погашенный ключ. При недоступном сервере тестовый вход не обходится кнопкой «продолжить без обновления»: доступ нужно проверить повторно либо вернуться к обычной версии.

## Выпускать версии

В обычной папке меняются только стабильный код и стабильный `launcher-channel.json`. В приватной папке меняются тестовый код, `testing-build.json` и тестовый `launcher-channel.json`; следующая версия — `0.1.0-test.3`. Проверенные функции переносятся отдельно, а не копированием всех файлов между репозиториями.

Для исходного механизма обновления по-прежнему нужен .NET SDK 8 x64. Сервер предоставляет разрешённые Git-объекты, клиент проверяет размер и SHA-1 каждого файла, собирает выбранную версию и сверяет ProductVersion перед установкой.
